Phase 01 Structured AI Response Layer
Start here Foundation
P1-T1 · PROMPT ENGINEERING
Design the universal AI response envelope
Every AI call must return a structured JSON payload — not just a message string. Modify the existing chatbot prompt to always respond in this schema. The AI does emotion analysis as part of the same call, no second call needed.
{
  "message": "string", // therapist reply text
  "emotion": "anxious|calm|sad|angry|hopeful|neutral",
  "intensity": 0.0–1.0, // emotion strength
  "stress_level": 0.0–1.0, // inferred stress
  "crisis": true|false, // crisis flag
  "suggestions": ["string"], // 0–2 quick actions
  "mood_tag": "string" // for timeline storage
}
P1-T2 · RESPONSE PARSING
Build a safe JSON parser middleware
LLMs sometimes return malformed JSON or wrap it in markdown fences. Write a parseAIResponse() utility that strips fences, attempts JSON.parse, validates required fields, and falls back gracefully to a plain text response with default emotion values if parsing fails.
// utils/parseAIResponse.js
function parseAIResponse(raw) {
  const cleaned = raw
    .replace(/```json|```/g, '').trim();
  try {
    const parsed = JSON.parse(cleaned);
    return validate(parsed); // fill missing fields
  } catch {
    return fallback(raw); // safe default envelope
  }
}
P1-T3 · PERSONALITY SYSTEM
Therapist personality prompt injection
Store therapist personality configs in Firestore under /personalities/{id}. Each doc has a system_prompt, name, tone, and avatar_ref. On session start, fetch the chosen personality and prepend its system_prompt to every AI call. Custom characters store user-authored prompts in the same collection under /users/{uid}/personalities/{id}.
  • GET /personalities — list all built-in personalities
  • POST /personalities/custom — create user custom character
  • Session middleware injects personality into each AI request

    Phase 02 Emotion, Mood & Stress Tracking
    After phase 1 Analytics
    P2-T1 · MOOD LOGGING
    Persist emotion data per message to Firestore
    After every AI response, extract emotion, intensity, and stress_level from the envelope and write them to /users/{uid}/moodLog/{YYYY-MM-DD} as an array of timestamped entries. This builds the raw data for the timeline and heatmap. Do not wait for the user to explicitly log — it's automatic and silent.
    moodLog/{YYYY-MM-DD}: {
      entries: [{
        ts: Timestamp,
        emotion: "anxious",
        intensity: 0.7,
        stress: 0.6,
        sessionId: "string"
      }]
    }
    P2-T2 · TIMELINE API
    Build mood timeline and heatmap endpoints
    Flutter needs pre-aggregated data — don't make the client compute. Build two read endpoints that aggregate the raw moodLog entries into timeline and heatmap formats the frontend can render directly.
  • GET /mood/timeline?days=30 — returns daily emotion arrays sorted by time
  • GET /mood/heatmap?weeks=12 — returns {date, avg_stress} for calendar heatmap
  • GET /mood/summary — returns weekly emotion breakdown percentages
  • All endpoints scoped to authenticated user via Firebase Auth middleware
    • P2-T3 · DAILY INSIGHTS ENGINE
    Generate daily insights and inspirational prompts
    Every day at midnight UTC, run a Cloud Function (Firebase Scheduled Function) that reads the user's last 7 days of moodLog, calls the AI with a summarization prompt, and writes a structured insight object to /users/{uid}/insights/latest. The Flutter app reads this on app open. Also generate an inspirational prompt tailored to the user's dominant recent emotion.

    Phase 03 Long-Term Memory System
    After phase 2 Intelligence
    P3-T1 · SESSION SUMMARIZATION
    Auto-summarize sessions into memory blobs
    After every 10 messages in a session (or on session close), trigger a background job that sends the last 10 messages to the AI with the instruction: "Summarize this therapy exchange in under 150 tokens, preserving key emotional themes, concerns raised, and any breakthroughs." Store the summary in /users/{uid}/memory/{memoryId} with a timestamp.
    memory/{id}: {
      summary: "string (≤150 tokens)",
      themes: ["anxiety", "work"],
      createdAt: Timestamp,
      sessionId: "string",
      messageRange: [0, 10]
    }
    P3-T2 · CONTEXT INJECTION
    Inject memory blobs into new session prompts
    On session start, fetch the 3 most recent memory blobs for the user and inject them into the system prompt as "Previous session context." Cap injected memory at ~400 tokens total to avoid bloating the context window. The AI will naturally reference past conversations without being explicitly told to.
    // services/memory.js
    async function buildContextPrompt(uid, personalityPrompt) {
      const blobs = await getRecentMemory(uid, 3);
      const memCtx = blobs.map(b => b.summary).join('\n');
      return [personalityPrompt,
        `Past context:\n${memCtx}`].join('\n\n');
    }
    P3-T3 · MEMORY MANAGEMENT
    Memory pruning and retrieval API
    Over time memory blobs accumulate. Keep only the most recent 20 blobs per user. Add a Cloud Function that runs weekly to prune old blobs. Also expose a DELETE /memory endpoint so users can clear their memory from the app settings screen (privacy feature).
  • GET /memory — list user's memory blobs (for settings UI)
  • DELETE /memory — clear all memory (GDPR-style right to erase)
  • Weekly Cloud Function prunes blobs older than 60 days if count > 20
    • P3-T4 · THEME TRACKING
    Extract and track recurring themes across sessions
    Each memory blob includes a themes array (e.g. ["anxiety", "relationships", "work"]). Aggregate these across the user's blobs to maintain a /users/{uid}/themeProfile document that counts frequency of each theme. This powers future insight generation and lets the AI reference recurring patterns.
  • On each memory write, update themeProfile with new theme counts
  • GET /themes — returns top themes with frequency for UI display
  • Inject top 3 themes into daily insight generation prompt
    • Phase 04 Crisis Detection & Safety Layer
    After phase 1 Critical
    This phase can be built in parallel with phases 2–3 since it hooks into the response envelope from Phase 1. Crisis detection is non-negotiable — it must be server-side and cannot be bypassed by the client.
    P4-T1 · CRISIS FLAG HANDLER
    Server-side crisis detection and response routing
    When the AI response envelope returns crisis: true, the backend must intercept before sending to the client. Log the crisis event to /crisisLog/{uid}/{timestamp} with the session context (no message content for privacy). Apply a 60-second cooldown on that user's session. Return an augmented response that includes crisis_mode: true and a resources array alongside the normal message.
    // Crisis response envelope
    {
      message: "string",
      crisis_mode: true,
      resources: [{
        name: "Crisis Helpline",
        number: "string",
        url: "string"
      }]
    }
    P4-T2 · SECONDARY DETECTION
    Keyword-based secondary crisis scanner
    The AI is the primary detector, but add a lightweight keyword scanner as a safety net that runs before the AI call on incoming user messages. If high-risk keywords are present, set a flag that tells the AI to evaluate crisis risk explicitly. This catches cases where the AI might be misled by context.
    // middleware/crisisScanner.js
    const HIGH_RISK = ['suicide', 'end my life',
      'hurt myself', 'can't go on'];

    function scanMessage(text) {
      return HIGH_RISK.some(k =>
        text.toLowerCase().includes(k));
    }
    // If true, prepend crisis-eval instruction to system prompt
    P4-T3 · RATE LIMITING
    Per-user session rate limiting and abuse prevention
    Implement rate limiting at the session level: max 60 messages per hour per user (configurable). Use a sliding window counter stored in Firestore or in-memory cache (Redis if available, otherwise Firestore). Return HTTP 429 with a retry-after header. Also implement a global per-IP limit for unauthenticated requests.
  • 60 messages / hour / user — sliding window
  • 5 sessions / day / user — prevents abuse
  • POST /admin/limits — admin endpoint to adjust limits per user tier
  • Return 429 with { retryAfter, message } — Flutter shows cooldown UI
    • P4-T4 · CRISIS LOG
    Crisis event logging for safety audit trail
    Every crisis flag must be logged for audit purposes — no message content, only metadata. The log is write-only from the app server and can only be read by admin service account. Store in /crisisLog/{uid}/{eventId}. This supports safety review without compromising user privacy.
    crisisLog/{uid}/{eventId}: {
      triggeredAt: Timestamp,
      sessionId: "string",
      detectedBy: "ai|keyword",
      resolved: false
      // NO message content stored
    }
    Phase 05 Encryption, Storage & Privacy
    After phase 1 Security
    P5-T1 · E2E ENCRYPTION
    Implement client-side E2E encryption for chat
    The backend must never store plaintext messages. Architecture: Flutter generates a symmetric AES-256 key per user, encrypts it with the user's device key, and sends only the encrypted message payload to the backend. The backend stores the ciphertext. For multi-device, use a key exchange flow (generate key on first device, re-encrypt for second device on login).
  • Backend stores: { ciphertext, iv, sessionId, timestamp } — no plaintext
  • POST /messages — accepts encrypted payload, writes to Firestore as-is
  • GET /messages/{sessionId} — returns ciphertext, Flutter decrypts locally
  • Backend has zero knowledge of message content

    Build complete chat history CRUD endpoints
    Sessions and messages need full lifecycle management. Flutter needs to load history on app open, delete individual sessions, and export all data (GDPR compliance). All endpoints require Firebase Auth JWT validation via middleware.

    P5-T3 · OFFLINE SYNC
    Offline queue and sync-on-reconnect mechanism
    When Flutter is offline, messages are queued locally with a status of "pending." On reconnect, Flutter sends queued messages in order to POST /messages/batch. The backend processes them sequentially, generates AI responses, and returns them all. Each queued message includes a client_id so Flutter can match responses back to local messages.
    // Batch sync request body
    {
      messages: [{
        client_id: "uuid",
        ciphertext: "string",
        timestamp: "ISO string"
      }]
    }
    P5-T4 · AUTH MIDDLEWARE
    Firebase Auth JWT validation on all routes
    Every API route must validate the Firebase Auth ID token from the Authorization header. Write a single verifyToken middleware that calls admin.auth().verifyIdToken(), attaches the decoded uid to req.user, and rejects with 401 on failure. Apply it globally — no route should be accessible without a valid token except health check.
    // middleware/auth.js
    async function verifyToken(req, res, next) {
      const token = req.headers.authorization?.split(' ')[1];
      if (!token) return res.status(401).json({error:'No token'});
      const decoded = await admin.auth().verifyIdToken(token);
      req.user = decoded; // { uid, email, ... }
      next();
    }
    Phase 06 Streaks, Gamification & Notifications
    Final phase Engagement
    P6-T1 · STREAK ENGINE
    Daily streak tracking with grace period
    A streak increments each day the user sends at least one message. Store in /users/{uid}/streaks/current. Include a 48-hour grace period (user can miss one day without losing streak) to reduce frustration. A Cloud Function runs nightly to evaluate and update streaks.
    streaks/current: {

      lastActiveDate: "YYYY-MM-DD",
      graceUsed: false,
      totalDays: 45
    }
    P6-T2 · PUSH NOTIFICATIONS
    Daily check-in reminders via FCM
    Use Firebase Cloud Messaging to send daily reminder notifications to users who haven't chatted that day. A Cloud Function runs at the user's preferred reminder time (stored in their profile). Also send a notification when a new daily insight is ready. Store FCM tokens in /users/{uid}/fcmTokens and handle token refresh.
  • Store FCM token on POST /auth/device — update on app launch
  • Scheduled Function: send reminders at user-set time (default 9am local)
  • Send insight-ready notification after daily insight generation
  • Handle token expiry — remove invalid tokens from Firestore

    Expose streak and engagement stats endpoints
    Flutter needs to display streak info, badges, and total engagement stats on the profile screen. Build a single aggregated endpoint that returns all engagement data in one call to minimize round trips on app load.
    // GET /stats → returns:

    P6-T4 · HEALTH CHECK & MONITORING
    Production readiness — health, logging, error tracking
    Before going live, add operational infrastructure. A GET /health endpoint for uptime monitoring. Structured JSON logging on every request and AI call (duration, tokens used, userId hash). Error tracking via a service like Sentry. Firebase App Check to prevent unauthorized API access from non-app clients.
  • GET /health — returns { status: 'ok', uptime, version }
  • Request logger middleware — logs method, path, uid hash, duration
  • AI call logger — logs model, tokens_in, tokens_out, latency_ms
  • Enable Firebase App Check — blocks non-app API access
  • Set up Sentry (or equivalent) for unhandled exception tracking
